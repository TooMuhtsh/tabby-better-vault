Vérification de faisabilité — à faire avant tout code

Bloquant

Confirmer que VaultService (ou l'équivalent réel dans le tabby-core installé) expose une méthode d'injection programmatique du mot de passe maître utilisable depuis un plugin tiers. Vérifier les DEUX niveaux : typings/index.d.ts ET le bloc d'export webpack réel de dist/index.js compilé — ne jamais conclure sur un seul des deux (même discipline que les pièges #6/#13/#17 du projet frère, voir AI-CONTEXT.html).

Si cette vérification échoue (méthode non exposée, ou trop verrouillée pour être pilotée depuis l'extérieur), tout le design ci-dessous est à revoir avant de commencer — ne pas scaffolder le plugin en attendant.

Scaffold du plugin

Pas encore commencé. Probablement la même mécanique que tabby-better-sidebar à son lancement (voir son historique pour le détail de ce qui avait été fait) :

  • Environnement de dev (Node.js, versions verrouillées Angular 15).
  • Scaffold package.json/tsconfig.json/webpack.config.js/LICENSE.
  • Jonction NTFS de dev dans %APPDATA%\tabby\plugins\node_modules\tabby-better-vault (pas TABBY_PLUGINS, cassé sur Windows).
  • Dépôt Git créé — .AIRules/ à déplacer dans ce dépôt dès sa création, pas à le laisser au niveau Développement/ (leçon du projet frère).

Déverrouillage automatique du coffre-fort

Objectif : éviter la ressaisie du mot de passe maître de Tabby à chaque démarrage, en déléguant le chiffrement à l'OS plutôt qu'en stockant le mot de passe en clair.

Délégation à l'OS via electron.safeStorage

  • Windows : Gestionnaire d'identifiants / DPAPI.
  • macOS : Trousseau d'accès (Keychain), avec Touch ID si activé.
  • Linux : Secret Service API (libsecret) via GNOME Keyring/KWallet.

Flux d'injection

  1. Mécanisme opt-in (à activer explicitement dans les options du plugin — jamais actif par défaut sans action explicite de l'utilisateur).
  2. Au démarrage, déchiffrement du token via l'OS puis tentative d'injection programmatique dans le VaultService de Tabby, avant que la pop-up native de saisie n'apparaisse.
  3. Garde-fou si l'injection échoue (ex. mot de passe maître changé depuis les réglages natifs de Tabby) : suppression immédiate du token local obsolète, retour transparent à la pop-up native — jamais d'erreur bloquante affichée à l'utilisateur pour cette fonctionnalité de confort.
Sécurité RAM — non négociable

La variable JS contenant le mot de passe maître déchiffré en clair doit être immédiatement écrasée (= null) dès que l'injection dans le moteur de Tabby est validée, pour limiter au minimum la fenêtre d'exposition du secret en mémoire vive. À respecter dès le premier prototype, pas seulement en version finale.

Stockage du token local

Le token chiffré (nom de clé à définir, ex. vaultAutoUnlockToken) est strictement local à la machine — ne doit jamais être exportable/synchronisable (contrairement aux réglages classiques d'un plugin). Si ce plugin gagne un jour ses propres réglages persistés dans config.yaml via ConfigProvider, cette clé doit être explicitement exclue de tout mécanisme d'export/partage — voir la discipline équivalente déjà appliquée aux workspaces de tabby-better-sidebar (son ROADMAP.html, où l'export ne porte jamais sur les données sensibles).

Interfaçage avec tabby-better-sidebar

Optionnel, pas une dépendance dure : tabby-better-sidebar doit continuer à fonctionner normalement si ce plugin n'est pas installé.

  • Tous les plugins Tabby tournent dans le même process Electron et partagent le même injecteur Angular — c'est le mécanisme déjà utilisé par tabby-better-sidebar pour consommer des classes de tabby-core/tabby-settings/tabby-ssh.
  • tabby-better-vault exporterait un service minimal (ex. VaultBridgeService) ; tabby-better-sidebar l'importerait en dépendance npm optionnelle, avec @Optional() côté Angular (ou Injector.get(TOKEN, null)) pour ne jamais planter si ce plugin n'est pas installé — la section correspondante des réglages disparaît simplement dans ce cas côté sidebar.
  • Pattern non officiel : effet de bord du chargeur de plugins partageant un même injecteur, pas une API documentée par Tabby. Le contrat entre les deux packages est à notre charge (versioning à gérer entre les deux — envisager de figer une interface minimale tôt pour éviter la casse croisée).
  • Même discipline de vérification que le reste de l'écosystème : si un service est exporté, vérifier les DEUX niveaux (typings ET bundle compilé) avant que l'autre plugin ne s'y fie.
